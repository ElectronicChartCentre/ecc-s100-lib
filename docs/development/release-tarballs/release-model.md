# Release Model and Tarball Naming

The repository is an npm workspace, but consuming applications should not depend
on the workspace root. They should depend on individual package tarballs.

## Release Targets

Current release targets are defined in
[`tools/release-targets.mjs`](../../../tools/release-targets.mjs):

- `@ecc/s100-viewer`
- `@ecc/s100-viewer-adapter-nasa-ammos`
- `@ecc/s100-viewer-adapter-cesium`

The helper script
[`tools/run-release-targets.mjs`](../../../tools/run-release-targets.mjs) runs
`check`, `test`, `build`, and `pack` across exactly that target list.

## Non-Release Packages

Reference or local packages are not published by this workflow:

- `@ecc/s100-viewer-adapter-three` is the plain Three.js reference adapter. It
  is useful for adapter-authoring and engine-switcher validation, but it is not
  a release target yet.
- The Cogs adapter remains outside the maintained package release set.

## Asset Names

`npm pack` generates tarball names from the npm package names and version. For a
version such as `0.1.0-alpha.13`, the expected asset names are:

```text
ecc-s100-viewer-0.1.0-alpha.13.tgz
ecc-s100-viewer-adapter-nasa-ammos-0.1.0-alpha.13.tgz
ecc-s100-viewer-adapter-cesium-0.1.0-alpha.13.tgz
```

The GitHub Release tag convention is:

```text
ecc-s100-lib-v0.1.0-alpha.13
```

The corresponding consumer URL pattern is:

```text
https://github.com/ElectronicChartCentre/ecc-s100-lib/releases/download/ecc-s100-lib-v0.1.0-alpha.13/ecc-s100-viewer-0.1.0-alpha.13.tgz
```

Do not rename tarballs after packing unless every consumer URL is updated to the
renamed asset. The least surprising path is to keep the names generated by
`npm pack`.

## Immutability Rule

Use one immutable GitHub Release per package version. Prefer creating a new
alpha version rather than replacing assets on a release that another application
may already have consumed.
